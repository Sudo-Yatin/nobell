01Scope of this document

System Architecture explains why these pieces exist and how they fit together. This document is the concrete shape of each piece — table columns, endpoint contracts, JSON formats — so implementation has one place to check rather than guessing from prose. Field names below are illustrative and will drift as we build; the relationships and reasoning behind them should not.

02Entity overview

Ten entities cover the whole system. Everything else is a join or a derived view.

Retailer → Store → Associate → Shift → Audio chunk → Conversation is the main spine. Store → Rubric → Rubric item feeds Score, which references a Conversation and a Rubric item.

07Storage layout

Object storage paths are namespaced by retailer and store from day one, so per-tenant access control and eventual data export are structural, not bolted on.

// audio chunk
retailers/{retailer_id}/stores/{store_id}/shifts/{shift_id}/chunk-{sequence_no}.opus

// transcript, if retained beyond processing
retailers/{retailer_id}/stores/{store_id}/conversations/{conversation_id}/transcript.txt

Whether the audio path is deleted immediately after transcription or retained for a window is the open retention decision — see roadmap.

08Mobile → backend API

A small, deliberately boring set of endpoints. Everything interesting happens after upload, not in the API surface itself.

EndpointPurpose
POST /shifts/startCreates a shift row. Fails if consent is not on file for the associate.
POST /shifts/{id}/chunksMultipart upload of one Opus chunk plus sequence number.
POST /shifts/{id}/endMarks ended_at, flushes any buffered chunk uploads.
GET /associates/{id}/feedback/latestIn-app read of the most recent daily feedback message.

09Backend → Voicemaker API

Called from a Supabase edge function, triggered on chunk upload. Sends the Opus audio and requests diarized output. Payload is capped by Voicemaker at roughly 100 MB per request — our ~2-3 MB chunks leave large headroom, which is intentional; see upload & chunking for why chunk size is small by design rather than by necessity.

Multi-channel diarization is not enabled on Voicemaker's side yet — until it is, responses carry text without a reliable speaker label, which blocks segmentation and scoring.

10Rubric JSON format

What a retailer's rubric looks like on the wire — human-editable, versioned, weights summing to 1.0.

{
  "store_id": "...",
  "version": 1,
  "items": [
    {
      "label": "Greeting",
      "description": "Associate speaks first, within ~30s, with a warm opening rather than 'yes?'",
      "weight": 0.10
    },
    {
      "label": "Needs discovery",
      "description": "Asks about use case, budget, or who the product is for before recommending",
      "weight": 0.25
    }
  ]
}

See what "good" means for why this is retailer-authored rather than something we impose.

11Scoring prompt structure

The scoring call takes a diarized transcript and the active rubric, and must return structured output — never freeform prose, so the app can render scores and quotes reliably.

// input
{
  "transcript": "[Associate] ... [Customer] ... [Associate] ...",
  "rubric": { /* as above */ }
}

// required output shape, one entry per rubric item
{
  "item_scores": [
    {
      "label": "Needs discovery",
      "score": 0.8,
      "justification": "Asked about intended use before recommending a model",
      "quote": "what will you mainly be using the phone for?"
    }
  ],
  "scoreable": true,
  "unscoreable_reason": null
}

unscoreable_reason exists so the model has an explicit way to say "the customer's side is inaudible" or "this conversation is too short to judge" rather than forcing scores onto thin evidence. Output is validated against this schema; a response that fails validation is retried once, then marked unscored — see failure handling.

12Retention & deletion jobs

  • Transcripts: a scheduled job deletes conversations.transcript content 90 days after creation, per the PRD's privacy commitments. Aggregate scores are unaffected — they do not reference transcript text.
  • Raw audio: whether audio_chunks objects are deleted immediately after successful transcription, or retained for some window, is still open — see the roadmap. The schema supports either without migration: deletion is a storage-layer job, not a schema change.
  • PII stripping: runs as part of the transcript write, before conversations.transcript is persisted — phone numbers, names, card numbers, addresses are redacted at write time, not after the fact.
